# StarIntel 0.10.1 bundle prerequisites

Scope updated 2026-10-10: focus only on canonical 0.10.1 alignment and its
complete compatibility bundle. Earlier next-version planning is withdrawn;
this document does not propose a future version or release transition.
Tracking: #204 and fleet alignment #196.

## Verified baseline

Main was `fa1c8f4fb0590526c39aa3e9bc4a7e6eac30bea7` when inspected.
The final generator, finalizer and consumer verifier explicitly target 0.10.1.
The reference compatibility reader also explicitly targets 0.10.1. A package
release, a document wire version, a source commit and a historical read profile
are different identities.

The 0.10.1 release-lock blob is identical at upstream commits `96d26c338078676ec1dc6928755901636c9f7ef0`
and `fa1c8f4fb0590526c39aa3e9bc4a7e6eac30bea7` (`c8336c3f427b14e341f1f4b72b5dc4ba32036c64`).
Their compatibility registries also have the same blob (`3aa632d7de6fca03498b8c1f8b23a1555259f2e8`).
This establishes identical declared locks, not a substitute for checking every
artifact. The registry's `canonicalCommit` remains source provenance; a newer
transport commit must not silently replace it.

## Prerequisite slice

The consumer tool rejects noncanonical path spellings, control characters,
backslashes, symlink targets and duplicate canonical-source mappings in online
and offline checks. Sync validates all destination paths before writing files
and writes its consumer lock last. The existing release-only directory layout
and public sync/check signatures remain unchanged.

This is protection against a static malformed checkout or lock, not a claim to
prevent a hostile process racing filesystem mutations. Sync is not a filesystem
transaction and does not roll back existing files after interruption. Consumers
must run the complete check before using any newly synced files. Atomic staged
bundle activation and interruption tests remain work under #204.

## Complete 0.10.1 bundle

1. Preserve the existing release-lock and generated bytes. Add a separate bundle
   lock over the release lock and the compatibility registry, reader, numeric
   helper, historical schema and fixtures. Exclude self-hashing/cycles.
2. Retain `0.10.1/` and `compatibility/` as siblings. Flattening the reader into a
   language SDK release directory breaks its authority-owned relative paths.
3. Make bundle mode opt-in with explicit release selection and immutable commit
   pins. Verify all bytes and mappings before staging; publish the lock last.
4. Test the relocated reader offline with actual read, dry-run, migrate and
   exact-byte restore operations. Exercise corruption, missing files, unsupported
   profiles, wrong versions, interrupted writes and path/mapping attacks.
5. Generate locks through the actual finalizer. CI may upload generated outputs
   for review with read-only repository permission; it must not push or publish
   releases automatically. Check committed generated bytes against regeneration
   at the final PR head.

A machine-readable capability matrix and bounded fuzzing must distinguish the
51-type historical schema, the 28 mapped historical migration dtypes, canonical
identity reads, archival recovery, individual SDK adapters and unsupported
profiles. Passing canonical serialization is not historical-reader support.
The executable-only legacy dialect, nested 0.10.1, unpinned 0.7.3 and arbitrary
downgrade remain unsupported by this reference.


## Fleet acceptance

Establish the same verified 0.10.1 contract at every actual downstream creation,
validation, serialization and ingestion boundary. Record exact library/application
pins, lock digests, supported profiles and runtime test results. Matching version
strings are insufficient. Missing producers and unapproved extension contracts
remain explicit blockers. Keep all changes in scoped draft PRs with exact-head
CI; no merge, tag, release publication or production corpus rewrite is included.
